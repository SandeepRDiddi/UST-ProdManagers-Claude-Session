01Concept · 8 min

The Real Gap: Retries Without Idempotency

notification-service's send() retries up to 2 times on failure — correct for one failure mode, dangerous for another.

  • Failure mode 1 (retry is correct): the provider never received the request. Retrying is exactly right.
  • Failure mode 2 (retry causes a bug): the provider processed the request successfully, but the response was lost — a timeout, a dropped connection. send() can't tell these two cases apart today, so it retries both the same way, and failure mode 2 means the customer gets duplicated.
  • The real, standard fix: the client supplies an idempotency key — a string generated once per logical request. The server recognizes a repeat key and returns the prior result instead of repeating the side effect. This is the exact pattern Stripe, AWS, and Twilio all use publicly for this exact reason.

In the reference implementation, where does the idempotency check happen?

  • A. After the retry loop finishes
  • B. At the very top of send(), before the retry loop starts

Why is a failed send deliberately NOT cached under its idempotency key?

  • A. To save storage space
  • B. So a fresh request with the same key can still succeed on a later retry
  • C. Failures are too rare to matter
  • D. It actually is cached — this is a trick

03Concept · 8 min

Cost Per Shippable Feature (and the Real Counter-Argument)

A real, current (2026) FinOps metric layer, and a real, current pushback worth knowing before you present either one as settled.

The metric stack
Cost per inference (one model call) → aggregated into Cost per Feature (every inference tied to one capability) → aggregated into Cost per Customer → combined with infrastructure into Cost-to-Serve. Different stakeholders care about different layers — engineering watches inference cost, finance watches cost-to-serve.
The counter-argument
A real, current pushback in the industry: hard per-developer spending caps optimize the wrong thing. The metric that actually matters is developer throughput — features shipped, incidents avoided — not the size of the token bill. A team that under-spends on tokens by capping aggressively can easily cost more in slower delivery and missed fixes than it saves in API spend.

Both are legitimate — that tension is the actual content of this concept, not a mistake to resolve before Lab 3. Your framing in Lab 3 should acknowledge it, not pretend one side won.
