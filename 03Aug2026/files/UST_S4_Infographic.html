Spot the Stale Doc

Think of a real README, wiki page, or architecture doc from your own work that you know is out of date. 60 seconds each: tell your partner what it claims, what's actually true now, and — if you can guess — roughly how long it's been wrong.

01Concept · 10 min

Why Docs Lie But Code Doesn't

Not a claim about any particular team's discipline. It's structural: a README is a snapshot someone wrote once. The code is the live state of the system — it has to be, because it's what actually executes.

  • Nothing forces a snapshot to track the live state. Several things force the live state to stay internally consistent — it has to compile, pass tests, and run in production.
  • The confidence with which a claim is stated has no relationship to how true it is. A README can say something false in exactly the same font size as something true.
  • The only way to tell the difference: check the claim against a source that has some mechanism forcing it to stay honest.

The Trust Hierarchy

A ranked way to resolve conflicting sources — not a moral judgment on any of them, just a reflection of what mechanism, if any, keeps each one honest.

Rank 1
Automated tests passing right now — encodes literal pass/fail behavior. If green, the behavior it describes is true at this exact commit.
Rank 2
The running source code itself — executed exactly as written; cannot silently disagree with itself.
Rank 3
Machine-enforced config, schemas, types, migrations — validated by the system at startup or runtime; wrongness breaks something quickly.
Rank 4
Commit history & PR discussion — shows why and roughly when a change happened, even if docs never caught up.
Rank 5
Code comments — closer to the code than docs, but enforced by nothing.
Rank 6
README / wiki / architecture docs — written once, read by many, updated by few.
Rank 7
Tribal knowledge — Slack threads, "ask so-and-so." Highest variance, least reproducible.

Rule of thumb: when two sources conflict, trust the one higher on this list — and verify any Rank 5–7 claim against a Rank 1–3 source before repeating it to a client.

Pop Quiz · 1

  • A. Automated tests passing right now
  • B. README / architecture docs
  • C. Code comments
  • D. Tribal knowledge / Slack threads
Answer: A. If a test is green, the behavior it describes is true at this exact commit — no interpretation gap.
02Concept · 18 min

Functional Context — What the System Is FOR

Framework: Domain-Driven Design — Bounded Contexts & Ubiquitous Language.

  • A bounded context is a boundary within which a domain model and its vocabulary are internally consistent. The same word — "Order," "Customer," "Claim" — can mean something different in Fulfillment than in Billing, and DDD says that's fine, as long as the boundary is explicit rather than silently assumed.
  • Ubiquitous Language is the vocabulary shared between domain experts and code, consistently, within one bounded context. The practical mining insight: the language actually embedded in class, function, and module names is the ubiquitous language in practice — whether or not it matches what the wiki calls things.

Source-mining technique

  • Extract the most frequently used domain nouns across the codebase — class names, top-level function names, database table names.
  • Cluster modules by which nouns they share. Where the vocabulary changes, or a translation/mapping layer appears, that seam is very likely a bounded context boundary.
  • Complementary technique: Event Storming (Alberto Brandolini) — a collaborative, sticky-note workshop with domain experts mapping domain events, commands, and aggregates. Use it when the code alone reveals structure but not intent.
Pop Quiz · 2

In DDD, what do we call the vocabulary that should stay consistent within one bounded context?

  • A. Event Storming
  • B. Ubiquitous Language
  • C. API Contract
  • D. Component Diagram
Answer: B. The bounded context is the boundary; Ubiquitous Language is the vocabulary that stays consistent inside it.
03Concept · 18 min

System Context — How the System Is BUILT

Framework: The C4 Model (Simon Brown) — four levels of zoom, each with a direct source-mining approximation.

Level 1
System Context
The system as one box: its users, and the other systems it talks to. Mine it from: outbound network calls / env vars for downstream URLs; inbound routes and auth scopes; message-queue topics.
Level 2
Container
The deployable/runnable units (services, databases, queues) and how they talk to each other. Mine it from: docker-compose.yml, Kubernetes manifests, Terraform; actual service-client instantiations in code.
Level 3
Component
The major structural building blocks inside one container. Mine it from: top-level package/module structure; dependency-injection wiring; the actual import graph.
Level 4
Code
Classes and functions. Mine it from: the source code itself — C4's own guidance is this level rarely earns a hand-drawn diagram, because the code already is the diagram. The strongest restatement of this session's thesis, from inside the framework itself.
Pop Quiz · 3

Which C4 level rarely needs a hand-drawn diagram, because the code already is the diagram?

  • A. Level 1 — System Context
  • B. Level 2 — Container
  • C. Level 3 — Component
  • D. Level 4 — Code
Answer: D. Even C4's own creator says Level 4 isn't usually worth hand-maintaining — the source is already the ground truth.
04Concept · 16 min

Data Context — What the System KNOWS

Framework: ODCS — Open Data Contract Standard (v3). A real, versioned, YAML-based standard describing a data product's schema, quality rules, SLAs, and ownership in one machine-readable artifact.

  • Fundamentals — name, owner, domain, description.
  • Schema — fields, types, and business definitions per field, not just column names.
  • Quality rules — constraints, freshness SLAs, null/uniqueness expectations.
  • Support & ownership metadata — who to contact, where it's discussed, lifecycle stage.

Why this fixes "docs lie" structurally, not procedurally: an ODCS contract is validated by CI — a malformed contract or schema drift breaks the build. Like tests, it has a built-in mechanism forcing it to stay true. A wiki-hosted "Data Dictionary.xlsx" has no such mechanism.

Source-mining technique when no contract exists yet (the common case)

  • Introspect the actual database schema directly — information_schema queries, ORM model definitions.
  • Read migration file history in order — a truthful, timestamped record of how the schema actually evolved.
  • Trace lineage from source tables through transformation code to any downstream consumer, rather than trusting a hand-drawn lineage diagram.
Pop Quiz · 4

What makes an ODCS contract more trustworthy than a wiki data dictionary?

  • B. It's validated by CI — a schema drift breaks the build
  • C. It has nicer formatting

Answer: B. Like tests, it has a mechanism forcing it to stay honest — the build breaks if it drifts from reality.
05Concept · 8 min

The Source-Mining Method

Six repeatable steps for using Claude Code to build accurate context on a new codebase — exactly what the demo runs end-to-end.

  1. 1. Read the docs first — for orientation, not truth. They tell you what to go verify, not what to believe.
  2. 2. Mine the tests. Rank 1 on the Trust Hierarchy — your strongest available evidence.
  3. 3. Mine the actual config, schema, and environment files. Rank 3 — machine-enforced, hard to get away with being wrong.
  4. 4. Mine commit and change history for anything recent the docs likely never caught up to.
  5. 5. Diff the docs' claims against Steps 2–4. Every mismatch becomes one line in a Context Discrepancy Report.
  6. 6. Produce the three-layer context brief — Functional, System, Data — from verified findings only. Anything unverifiable gets flagged, not silently assumed true.

Source-Mining, Live

A small, real Python service — notification-service — with a README, source, config, tests, and a changelog. Every discrepancy below has been verified by actually running the test suite. This is not a scripted illustration.

Repo: notification-service

Real repo · project-lumen.zip · tests pass as-is
  1. Read the docs first, for orientation2 min
    TYPE THIS"Read README.md. Summarize what it claims about supported channels, retry behavior, and rate limiting — in one line each."
    Expect: three clean, confident claims — Email/SMS only; 3 retries with exponential backoff; 100 req/s. Nothing hedged. That's the trap.
  2. Mine the tests5 min
    TYPE THIS"Now read tests/test_notification_service.py and run the test suite. For each of the three claims from README.md, tell me whether a test confirms it, contradicts it, or says nothing about it."
    Verified: all 5 tests pass, and directly contradict two of the three claims — a third channel (push) exists, and the real retry policy is 2 attempts with a fixed 2-second delay, not 3 with exponential backoff.
  3. Mine config and source directly5 min
    TYPE THIS"Read config/rate_limit_config.yaml and src/rate_limiter.py. What rate limit is actually enforced, and how confident can you be in that number?"
    Verified: requests_per_second: 50 in the config, loaded directly with no other code path — confirmed by running the service and reading its printed output: 50 req/s, not the 100 in README.md.
  4. Mine the change history3 min
    TYPE THIS"Read CHANGELOG.md. For each discrepancy we've found, when did the code change and why — and was README.md updated at the same time?"
    Expect: three dated entries, each explicitly noting README.md was not updated. This is where the room stops being surprised and starts being uncomfortable — these weren't neglect, they were reasonable engineering calls that never propagated to the doc.
  5. Produce the Context Discrepancy Report4 min
    TYPE THIS"Produce a Context Discrepancy Report: one row per claim, with the README's claim, the verified reality, the evidence source, and the date it diverged."
  6. Produce the three-layer context brief3 min
    TYPE THIS"Using only what we've verified — not README.md — write a short Functional, System, and Data context summary, and flag anything you still can't verify from source alone."
    Expect: a brief with the real numbers, and open questions (e.g. why push was added, who owns the service today) flagged for a human — not guessed.

Production-Readiness Checklist

After this session, you should be able to say yes to all of the following on a real, unfamiliar client codebase:

  • ☐ I can mine Functional, System, and Data context from an unfamiliar service within a defined time-box (target: 2 hours for a mid-size service).
  • ☐ I can produce a Context Discrepancy Report flagging doc-vs-code mismatches before relying on either in a client conversation.
  • ☐ I can apply the Trust Hierarchy to resolve two conflicting sources without asking someone else which one is right.
  • ☐ I can describe a service's System Context using C4's Level 1–2 vocabulary, sourced from real config and code.
  • ☐ I can identify bounded contexts and the actual ubiquitous language in use from code structure alone.
  • ☐ I can state which parts of a data model are verified from schema/contract versus assumed from a doc — and say so, out loud, in front of a client.
  • ☐ I know when to stop mining and escalate — "I can't verify this from source, I need a human" — rather than guess with false confidence.
Case Closed

Docs are optional to update. Code is not — it has to run. Everything after this session — Discovery Canvases, Agent-Ready Specs, Cost Models — is only as trustworthy as the context layer it's built on.
