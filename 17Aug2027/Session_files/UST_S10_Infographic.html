01Concept · 15 min

Spec-Driven Development — Why the Spec Became the Code

By 2026, spec-driven development (SDD) is mainstream: an executable, version-controlled specification — not the code — is the source of truth. The team writes the spec, derives a plan, breaks it into tasks, and only then generates code. When requirements change, you edit the spec and regenerate.

  • The origin: a direct reaction to "vibe coding" — the term Andrej Karpathy popularized in early 2025 for loosely prompting an agent and shipping whatever comes back. Fine for a throwaway prototype, unmaintainable at production scale.
  • The founding argument: Sean Grove (OpenAI), "The New Code," AI Engineer World's Fair 2025 — specs are the versioned, testable home of intent. Code becomes a generated, verifiable artifact rather than the thing humans directly author.
  • The four-phase workflow popularized by GitHub Spec Kit — now the de facto standard, agent-agnostic across 30+ tools: /specify → /plan → /tasks → /implement.
  • Real tooling landscape today: GitHub Spec Kit (open source, CLI-first), AWS Kiro (GA with CLI — requirements.md, design.md, tasks.md as first-class files, not an add-on), Claude Code Skills (an SDD workflow packaged as a reusable slash command), plus OpenSpec, BMAD-METHOD, Tessl, Google Antigravity, and Cursor's own rule files.
  • EARS (Easy Approach to Requirements Syntax) — a real, borrowed-from-aerospace format for writing acceptance criteria precisely: "WHEN [trigger], the [system] SHALL [response]." Turns a vague requirement into something an agent — or a test — can check mechanically.

The Maturity Model — How Much Should the Spec Actually Own?

Spec-anchored
Specs come before code and constrain what an agent generates. Code remains the primary deliverable — most teams' default in 2026.
Spec-as-source
The furthest end of the spectrum: specs literally become the source code, regenerated on every change. Powerful, but the antipattern ThoughtWorks warns about below lives here.

The honest caveat: the ThoughtWorks Technology Radar (Vol. 33, 2025) places SDD in its "Assess" ring — not "Adopt" — and explicitly warns against "a bias toward heavy up-front specification and big-bang releases." SDD is a real discipline, not a silver bullet; over-specifying before you understand the problem recreates the worst parts of waterfall with extra ceremony.

02Concept · 15 min

Governing Agents, Not Code

Traditional software governance reviews code, line by line, PR by PR. That doesn't scale once an agent can generate thousands of lines in minutes. The industry's real answer in 2026 isn't more review — it's moving governance to a different layer entirely.

  • The Productivity-Reliability Paradox (Farrag, cited in 2026 research on regulated-domain agentic engineering): "review everything" creates velocity collapse — Atlassian's own deployment of human-in-the-loop coding agents found the cost of human feedback consumed the entire productivity benefit. "Review nothing" creates unauditable code and real regulatory exposure.
  • The resolution — govern the spec and the action, not the diff: a 2026 paper on institutional AI governance formalizes this as "Governing Actions, Not Agents" — an agent retains full autonomy over planning and reasoning, but holds no execution authority over designated high-risk, irreversible actions (merge to main, deploy, delete a migration). Sound familiar — it's the same HITL-gate pattern from tiered autonomy, now applied specifically to the SDLC itself.
  • Governance as code: policy defined programmatically — versioned thresholds, RBAC on shared specs, an eval gate before a spec change ships — the same discipline infrastructure-as-code brought to deployment, now brought to the specs governing agent behavior.
  • The practical mechanism, in one line (industry practitioner framing, 2026): "compliance defines the required tests, automation checks them, and a human reviews only the exceptions." This is Gherkin-as-guardrail again — the spec's acceptance criteria are the enforcement layer, not a document a human re-reads on every change.
Value Add

An agent that can draft anything but execute nothing consequential without a gate isn't a slower agent — it's the only shape of "fast" that survives a regulator, an auditor, or a bad day, asking how a specific line of production code actually got there.

Pop Quiz · 2

Per the "Governing Actions, Not Agents" pattern, what does an agent retain full autonomy over even in a governed system?

  • A. Executing irreversible, high-risk actions
  • B. Planning and reasoning
  • C. Bypassing required tests
  • D. Merging directly to production
Answer: B. The gate sits at consequential execution, not at thinking — the agent can reason and draft freely; it just can't act on the highest-risk categories alone.
03Concept · 15 min

Token Spend by SDLC Phase — The New Cloud Bill

"Token spend is the new cloud bill" is a genuine 2026 framing — and the organizations blindsided by cloud overruns in 2018 are on track to repeat the exact pattern with AI token spend, for the exact same reason: nobody was watching where it went.

  • The scale is real: GitHub Copilot completed its move to token-based billing in mid-2026. A 100-developer organization mixing inline and agentic tools can reach $400,000–$600,000/year before any governance is applied — and roughly 80% of companies exceed their AI coding budget because spend stays invisible without structured tracking.
  • Token cost is non-linear: a 2026 enterprise assessment found that 3× task complexity can produce up to 27× token spend — most ROI models still assume linear scaling, and they're wrong every time a "slightly harder" ticket lands.
  • The counterintuitive finding: a 2026 empirical study of a multi-agent software development framework found the Code Review stage — not initial Implementation — accounted for the largest share of total token consumption, driven by iteration loops: re-checking, re-explaining context, re-generating after feedback.
  • Agentic overhead compounds: agentic workflows consume 5–30× more tokens per task than a simple chat exchange, because every step re-carries system prompts, tool definitions, and full context. Output tokens cost 4–6× more than input tokens across major providers — a real, concrete lever: shorter, tighter outputs save disproportionately.
  • The fix that's actually working — hybrid model routing: Paul Gauthier's published Aider benchmark (Jan 2025) combined a cheap reasoning model for planning with a frontier model for precise execution and hit state-of-the-art results at 14× less cost than a frontier-only approach. Planning tokens are 5–20× cheaper than execution tokens when tiered correctly, and good planning cuts execution retries by 40–60%.
