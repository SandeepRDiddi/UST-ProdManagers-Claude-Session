Icebreaker⏱ 5 min · whole room

Would You Delete This?

Facilitator shows one function, no other context: a private method that's never called anywhere in its own file. Show of hands: delete it, or leave it? Then: how confident are you, 1–5? Hold that vote — you'll find out at the end of Lab 2 whether the room was right, and Lab 4 will complicate the answer either way.

01Concept · 8 min

Dead Code = Broken Context

Nobody sets out to write dead code. It accumulates because deleting anything requires confidence that nothing depends on it — and confidence requires context. When context is broken, the safe default is to never delete anything, and dead code piles up as the visible symptom of an invisible problem.

  • Good context is what makes deletion safe. Bad context is what makes every deletion feel like a gamble — so nobody takes it, and the codebase only ever grows.
  • This isn't only a cleanliness problem. Every dead or half-dead function is a place a future reader — or a future agent — will misjudge what the system actually does.
  • Today's target: notification-service, the same repo from Session 4. Same codebase, new question — not "does the doc match the code," but "does every piece of this code still deserve to exist?"
02Concept · 8 min

The Diagnostic Lens

Four categories, built from the same three context layers as Session 4 — Functional, System, Data — now applied as a classification tool instead of a mining method.

LIVE
Called, and still serving a real capability. Leave it alone.
DEAD
Defined, never called, no external reason to exist. Safe to delete.
VESTIGIAL
Reachable in principle, but permanently gated off (a feature flag that will never flip back). Safe to delete once the flag's fate is confirmed.
ZOMBIE
Looks dead to internal analysis — but alive via something outside the repo: an external caller, a scheduled job, a public API contract. Do not delete without more context.

The lens is applying all three context layers before you trust any single signal: Functional (does a real use case still need this?), System (is it reachable in the real call graph, including callers outside this repo?), Data (does it operate on structures still in production use?).

L2Lab 2 · 25 min⚙ Code Execution

Prove It With Code Execution

Turn Lab 1's reasoning into a number. Ask Claude to actually write and run real static analysis — not describe what analysis would show.

Run: dead_code_scan.py

Real AST-based scan · verified output below
  1. Naive scan — one file6 min
    TYPE THIS"Using code execution, write a Python script that parses notification_service.py with the ast module, finds every function defined, finds every name called anywhere in the file, and reports which defined functions are never called. Run it."
    Verified output: 5 of 6 functions flagged dead, including send() — which we already confirmed is LIVE in Lab 1. This is the naive scanner being wrong, on purpose.
  2. Widen the scope8 min
    TYPE THIS"Now run the same analysis across notification_service.py, rate_limiter.py, AND tests/test_notification_service.py together. Does the answer change for send()?"
    Verified: send() is now correctly cleared — it's called from the test file. But 5 functions are still flagged, because scope alone doesn't fix everything.
  3. Find the scanner's blind spot7 min
    TYPE THIS"_provider_send() is still flagged as dead. Read how send() actually calls it — is this a real gap in our scan method, or a real dead function?"
    Verified finding: send_fn = self._provider_send assigns it to a variable, then calls send_fn(...) — a real, honest limitation of name-based static analysis. _provider_send() is genuinely LIVE; the scanner just can't see indirect calls.
  4. Reconcile with Lab 14 min
    TYPE THIS"Compare this scan's results with our Lab 1 classification. Where did they agree, and where did the code execution result change our answer?"
Verified numbers 7 functions total. Naive single-file scan flags 5 as dead (71%). Whole-repo scan still flags 5 — scope alone doesn't catch the indirect-call blind spot. Diagnostic Lens correctly narrows this to 2 genuinely DEAD, 1 VESTIGIAL, 1 false positive (actually LIVE), and 1 ZOMBIE needing a human call.
Pop Quiz · 2

Why did _provider_send() stay flagged as "dead" even after widening the scan to the whole repo?

  • A. It really is dead — the scanner is correct
  • B. It's called indirectly through a variable (send_fn), which name-based static analysis can't see

L4Lab 4 · 10 min🌐 Web Search🧠 Extended Thinking

Verify Against Reality + The Hard Judgment Call

Two more moves: check your method against the outside world, then sit with the one classification that genuinely can't be resolved from this repo alone.

Web Search + Extended Thinking

get_notification_status() — the ZOMBIE case
  1. Verify the method against real tools4 min
    TYPE THIS"Search the web for how real dead-code detection tools like vulture or coverage.py work. Does our AST approach match how they actually operate, and do they have the same indirect-call blind spot we found?"
    Expect: confirmation that name-based / coverage-based dead-code tools share this exact limitation — you didn't just build a toy, you rediscovered a known, real constraint of the whole tool category.
  2. Sit with the hard case6 min
    TYPE THIS"Think carefully, step by step: get_notification_status() has no caller anywhere in this repo, but it's documented as a public API entry point for external partner systems. Walk through every piece of evidence for and against deleting it, and tell me what additional information — outside this repo — would actually resolve this."
    Expect: Claude should explicitly reason through the uncertainty rather than picking a side quickly, and land on a concrete next step — e.g. "check the API gateway logs for real traffic to this endpoint" — not a guess dressed up as an answer.
Verdict The icebreaker vote gets its answer here: the function most rooms vote to delete on sight is exactly the kind of case where the right move is refusing to guess. Context that lives outside the repo is still context — and "I need more information" is a correct diagnosis, not a failure to reach one.
Pop Quiz · 4

What's the correct next step for a ZOMBIE-classified function?

  • A. Delete it — if nothing in the repo calls it, it's safe
  • B. Keep it forever, just in case
  • C. Go find the specific piece of context outside the repo that would actually resolve the question — e.g. real traffic logs
  • D. Ask the original author, if you can find them
Answer: C. Not "never delete" and not "delete anyway" — identify exactly what evidence would settle it, and go get that evidence.
